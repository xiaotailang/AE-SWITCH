# 原生工具写读验证的可靠性

验证继续要求同一次受控验证具备全部证据：客户端进程成功、受管 UUID 文件的写入事件、同文件的读取事件、关联的成功读取结果实际包含本次随机 marker、助手最终回复，以及磁盘文件的精确字节。任何一项缺失仍失败；程序不会替客户端修正文件内容、换行或编码。

## 本轮改进

- Windows Codex 的提示要求创建结束后，使用单独一次 shell 工具调用，通过 `Get-Content -LiteralPath ... -Raw` 或 `[System.IO.File]::ReadAllText(...)` 读取同一个精确路径。提示禁止用别名、字节数组、编码命令或 echo 代替独立读取。两个文本读取形式均已有事件识别支持，本次不扩大读取操作的字符串匹配范围。
- Hermes 的提示明确要求 `write_file` 的 content 仅含 marker 的 ASCII 字符，指出准确字符数，并禁止 BOM、LF、CR、前后空白和作为内容写入的引号。写入成功后须单独调用 `read_file`。精确文件检查仍不做 trim 或换行规范化。
- 成功返回 marker 的结果若显式声明非零或类型错误的 `exit_code` / `exitCode`，不能构成成功读回；检查覆盖结果本身以及已知的 state/result 包装。已知进行中、等待中及已取消/失败状态同样不能构成成功结果。正常开始事件的空 exit code 不妨碍随后独立的成功完成事件。

## 证据边界

之前一次 Codex 验证的脱敏事件摘要显示：完成事件输出含 marker，但操作未被识别为读取。摘要没有保留原始命令，因此不能确认它用了哪种读取方式，也不能把该失败改判为成功。本次改进使后续请求明确使用可观察的标准文本读取形式，不追溯修复旧验收记录。

之前一次 Hermes 验证的精确文件字节门禁未通过；换行或编码差异只是可能原因。提示加强后仍需用当前构建执行真实客户端验证，不能用提示变化或合成事件测试代替该验收。

本轮回归使用合成事件与 G 盘临时文件，覆盖两个标准文本读取形式、独立同 ID 完成、进行中事件、失败退出、错类型退出、错误路径/不关联结果、别名/字节数组/echo 拒绝，以及 Hermes 的精确字节拒绝。它们验证的是接受规则，不证明官方客户端或上游端点当前可用。
